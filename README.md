# Places: Next.js + Elysia + Drizzle + PostGIS + Better Auth

Save places to an account and search them by distance. One Next.js app serves the UI and a typed
Elysia API; PostgreSQL with PostGIS stores the data; Better Auth handles accounts; shadcn/ui builds the interface.
It is prepared for Vercel.

## Features

- Email + password accounts (sign up, sign in, sign out), protected dashboard and protected API routes.
- Places API: create, list (paginated), get, delete (owner only) and **nearby search** by radius in metres (PostGIS).
- Elysia API embedded in Next.js (`/api/*`) with end-to-end types through Eden Treaty.
- Central error handling, validation on every input, rate limiting, security headers, validated environment.
- Playground page to try the public endpoints; dashboard to manage places.

## Installation

Prerequisites: [Bun](https://bun.sh) 1.x, Node.js 20.9+ (Next.js runs on it), Docker (for local PostGIS).

```bash
bun install
cp .env.example .env     # then edit: at least BETTER_AUTH_SECRET and DATABASE_URL
```

Generate a secret with `openssl rand -base64 32`.

## Local development

```bash
docker compose up -d db          # PostgreSQL 16 + PostGIS 3.4 on localhost:5432
bun run db:migrate               # enables PostGIS, creates tables
bun run dev                      # http://localhost:3000
```

The compose file creates user `app`, password `app_dev_pw`, database `appdb`. They are local-development
credentials only, so the matching URL is `postgres://app:app_dev_pw@localhost:5432/appdb`.

- Use `bun run dev` (`next dev`) day to day. `vercel dev` is only needed if you want to emulate the platform.
- After changing a table in `src/db/schema/geo.ts`: `bun run db:generate`, **read the new SQL file**, then
  `bun run db:migrate`. Never edit generated migrations or `src/db/schema/auth.ts` by hand.
- After changing Better Auth options that add tables or fields: `bun run auth:generate`, then `db:generate`.
- Never use `drizzle-kit push` against anything but a throwaway local database.

## API reference

Base path `/api`. Every response is JSON. Success bodies have `"success": true`; failures use one shape:

```json
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "Request validation failed",
  "details": [{ "path": "/lon", "message": "..." }] } }
```

Error codes: `BAD_REQUEST` 400, `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409,
`VALIDATION_ERROR` 422, `RATE_LIMITED` 429 (with `Retry-After`), `INTERNAL_ERROR` 500 (generic message, details only in server logs).

| Method and path | Auth | Description |
| --- | --- | --- |
| `GET /api` | no | `{ "success": true, "name": "Elysia Backend API", "version": "1.0.0" }` |
| `GET /api/health` | no | `{ "success": true, "status": "healthy" }` |
| `POST /api/echo` | no | Body `{ "message": string }` (1 to 500 chars, not blank). Returns `{ "success": true, "data": { "message": "..." } }` |
| `GET /api/me` | yes | The signed-in user: `id`, `name`, `email`, `emailVerified`, `image`, `createdAt`. 401 otherwise |
| `POST /api/places` | yes | Body `{ "name": string (1 to 120), "longitude": -180..180, "latitude": -90..90 }`. 201 with the place. 409 if you already have a place with that name |
| `GET /api/places` | no | `?limit=1..100 (default 20)&offset=0..`. `{ "data": [place], "pagination": { "limit", "offset", "total" } }`, newest first |
| `GET /api/places/:id` | no | One place (`:id` must be a UUID; 404 if missing) |
| `DELETE /api/places/:id` | yes, owner | 200 `{ "success": true, "data": { "id" } }`. 403 for another user's place, 404 if missing |
| `GET /api/places/nearby` | no | `?lon=&lat=&radius=&limit=`. `radius` in metres, 1 to 50,000 (default 1000); `limit` 1 to 100 (default 20). Nearest first, each item has `distanceMeters` |
| `/api/auth/*` | n/a | Better Auth: `POST /sign-up/email`, `POST /sign-in/email`, `POST /sign-out`, `GET /get-session`, ... |

A place looks like:

```json
{ "id": "6f1c...-uuid", "name": "Corner Cafe", "longitude": 2.2945, "latitude": 48.8584,
  "ownerId": "user-id", "createdAt": "2026-11-06T10:00:00.000Z" }
```

Examples:

```bash
curl -s localhost:3000/api/health
curl -s -X POST localhost:3000/api/echo -H 'content-type: application/json' -d '{"message":"hello"}'

# nearby: places within 200 m, with distanceMeters
curl -s 'localhost:3000/api/places/nearby?lon=2.2950&lat=48.8584&radius=200'

# sign up (cookie jar), then create a place
curl -s -c jar.txt -X POST localhost:3000/api/auth/sign-up/email \
  -H 'content-type: application/json' -H 'origin: http://localhost:3000' \
  -d '{"name":"Ada","email":"ada@example.com","password":"a-long-password"}'
curl -s -b jar.txt -X POST localhost:3000/api/places -H 'content-type: application/json' \
  -d '{"name":"Corner Cafe","longitude":2.2945,"latitude":48.8584}'
```

Better Auth checks the `Origin` header on state-changing requests; send it from non-browser clients.

## Database and PostGIS notes

- **Column:** `places.location` is `geometry(Point,4326)`. SRID 4326 is WGS 84 longitude/latitude.
  **PostGIS order is (longitude, latitude)**, that is (x, y); the API uses `longitude` and `latitude` names to avoid mixups.
- **Why a custom type:** Drizzle's built-in `geometry()` ignores `srid` and emits `geometry(point)`. `src/db/types.ts`
  emits the full type so the database enforces SRID 4326. See `docs/DECISIONS.md` D-006.
- **Distances in metres:** queries cast to `geography`: `ST_DWithin(location::geography, origin::geography, metres)`.
  The GiST index is on that exact expression (`places_location_gist_idx`), which is why it is used.
  `EXPLAIN` on 20,000 rows is asserted to use it (`tests/db.test.ts`).
- **Never concatenate input into SQL.** Use Drizzle's `sql` template (bound parameters) as in
  `src/server/modules/places/service.ts`.
- **PostGIS objects:** `spatial_ref_sys` and friends belong to PostGIS; `drizzle.config.ts` filters them out.
- **Migrations:** `0000_enable_postgis.sql` runs first (`CREATE EXTENSION IF NOT EXISTS postgis`); the role running
  migrations must be allowed to create the extension.

### Running migrations in production

Run them as a deliberate step, never implicitly at runtime and never from the Vercel build:

```bash
# from CI or a trusted machine, with the production database's DIRECT (non-pooled) connection string
DATABASE_URL='postgres://...' bun run db:migrate
```

Read the new SQL first, take a backup or snapshot for destructive changes, and migrate **before** shipping code that
needs the change (or make the change backward compatible). Do not run it without the owner's approval.

## Authentication notes

- Sessions are cookie based (`better-auth.session_token`, `__Secure-` prefix over HTTPS). `nextCookies()` is the last plugin so
  Server Actions can set cookies.
- **Protection is layered:** `src/proxy.ts` only checks that the cookie exists (fast redirect). `requireSession()`
  validates the session against the database in the dashboard layout and page, and the Elysia `auth` macro
  does the same for `/api/me`, `POST /api/places` and `DELETE /api/places/:id`.
- **Vercel previews:** every deployment has a new URL. Leave `BETTER_AUTH_URL` unset for the Preview environment;
  the app then uses `VERCEL_BRANCH_URL` (or `VERCEL_URL`) as its origin and trusts both. Set `BETTER_AUTH_URL`
  for Production only.
- Auth rate limits are stored in the `rate_limit` table (production only). Email verification and password reset are not
  configured because no email provider exists (see Recommendations).
- Passwords, tokens and cookies are never logged by project code. Unexpected errors are logged server-side with
  their error object; for a failed Drizzle query that includes the SQL and bound parameters.

## Testing

```bash
bun run typecheck && bun run lint
bun run test          # 85 tests, ~3 s; creates a fresh `app_test` database from the real migrations
bun run build && bun run test:e2e   # 10 Playwright tests against `next start`
```

`bun run test` needs PostgreSQL + PostGIS reachable with `TEST_DATABASE_ADMIN_URL` (default: the compose database).
It never touches the database in `DATABASE_URL`. E2E tests create real users and places in that database.

What is covered: core endpoints and status codes; validation and error shape (no leaking of internals); auth flows;
places CRUD with owner/non-owner; nearby search against exact ellipsoid distances, a 111.32 m / 111.31 m radius boundary,
the antimeridian and the real Eiffel Tower to Louvre distance; SRID enforcement; migrations on a brand-new database;
GiST index usage; SQL injection attempts; rate limits; env validation; and a full browser flow.

## Deploying to Vercel

1. **Database:** create a hosted PostgreSQL that supports PostGIS and confirm
   `select * from pg_available_extensions where name = 'postgis'` returns a row. Neon documents PostGIS support
   (`CREATE EXTENSION IF NOT EXISTS postgis`); check any provider yourself before committing to it.
2. **Project:** `vercel login`, then `vercel link` in this folder. Vercel detects Next.js; no `vercel.json` is needed.
3. **Environment variables** (Production and Preview; names only):
   - Both: `DATABASE_URL` (pooled), `BETTER_AUTH_SECRET` (use different secrets per environment), optional `ALLOWED_ORIGINS`,
     `WRITE_RATE_LIMIT_MAX`, `DATABASE_POOL_MAX`.
   - Production only: `BETTER_AUTH_URL=https://your-domain`. Preview: leave unset.
4. **Migrate** the database (see "Running migrations in production").
5. **Preview deployment:** `vercel`. **Production:** `vercel --prod` (only after you have approved it and checked the preview).
6. Check `GET /api/health`, sign up on the preview URL, and create/delete a place.

### Function region

Put functions near the database. In `vercel.json` (create it only for this) set for example
`{ "regions": ["sin1"] }`, or use the project's Functions region setting. Confirm your plan's duration, memory
and bundle limits in the Vercel documentation.

### Runtime

Node.js (Vercel's default). Bun is used locally for installs, scripts and tests. Vercel supports a Bun runtime for
Next.js (beta); it is intentionally not enabled, see `docs/DECISIONS.md` D-003.

## Serverless notes

- **Stateless:** nothing relies on in-memory state across requests, except the best-effort write rate limiter
  (per instance, see D-010) and the module-level connection pool.
- **Connections:** one small pool per instance (`DATABASE_POOL_MAX`). Many concurrent instances times pool size must stay under your
  database's connection limit; use the provider's pooler.
- **Cold starts:** `elysia` is loaded from `node_modules` (D-007), `pg` and Better Auth load on first use, no heavy imports in the hot path.
- **Caching:** with Cache Components, Route Handler GETs are dynamic here because every handler awaits `connection()`.
  Nothing in the API is cached.
- **Realtime:** WebSockets do not work on Vercel Functions. If you need realtime, use a managed service (for example
  a pub/sub provider) instead of adding sockets to this app.
- **Files:** there is no persistent disk; use object storage if uploads are ever needed.
- **Background work:** use platform mechanisms (queues, cron, workflows), not timers in a function.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `extension "postgis" is not available` / `permission denied to create extension` | The server lacks PostGIS or the migration role cannot create extensions. Use a PostGIS image or provider, or have an admin run `CREATE EXTENSION postgis` once, then re-run the migration. |
| `Invalid environment variables:` at startup | A variable is missing or malformed; the message lists names. Fix `.env` / Vercel settings. |
| `Invalid origin` (403) from `/api/auth/*` | The request origin is not trusted. Match `BETTER_AUTH_URL`, add the origin to `ALLOWED_ORIGINS`, or send `Origin` from non-browser clients. |
| Sign-in works locally but cookies are lost on a preview URL | `BETTER_AUTH_URL` is set to another host in Preview. Unset it there. |
| `too many clients already` / timeouts under load | Pool size times instances exceeds the database limit. Lower `DATABASE_POOL_MAX`, use the pooled connection string. |
| Validation does not reject out-of-range query values after an upgrade | Run `bun run test:e2e`; see D-007 (`serverExternalPackages: ["elysia"]`). |
| A new endpoint returns 204 and fails with 500 in production only | See D-008; return 200 with JSON, or test it with `bun run test:e2e`. |
| A warning about an invalid source map for Elysia in the server log | Harmless noise from the package's source map. |
| `bun test` finds no PostgreSQL | Start `docker compose up -d db`, or set `TEST_DATABASE_ADMIN_URL`. |

## Recommendations (not implemented, by design)

- Shared rate limiting for writes (Vercel WAF rules, or Redis) when a hard global limit is needed.
- Email verification and password reset (needs an email provider); social sign-in, magic links or 2FA if wanted.
- A nonce-based `script-src` Content-Security-Policy (makes pages dynamic; see D-009).
- Observability: structured logging, error tracking, uptime checks on `/api/health` (consider a DB check on a separate endpoint).
- CI: run `typecheck`, `lint`, `test`, `build` and `test:e2e` on every pull request, and run migrations as a separate approved job.
- Automated database backups and point-in-time recovery with your provider.
- Keyset pagination if `places` grows large; a map UI on top of the nearby endpoint.
